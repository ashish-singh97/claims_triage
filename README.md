# Claims Triage — Senior Data Scientist Assignment

End-to-end, laptop-sized prototype for CMS DE-SynPUF Sample 1 carrier claims, with a fully runnable generated-data demo. Outputs: clean/denial-risk/FWA-risk probabilities, cost-based auto-approve/review/high-risk routing, plain-language reasons, a FastAPI service, tests and a generated technical note.

**Included artifacts are generated DEMO results, not results trained on downloaded CMS claims.** Run the CMS command below to replace them. Neither source contains real fraud outcomes. Performance against noisy simulated outcomes is not evidence of real-world fraud-detection quality.

## 1. Install (macOS/Linux)

Use Python 3.11 or 3.12. From the extracted `claims_triage` directory:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

`requirements-lock.txt` records exact versions tested in the supplied demo. Use it instead of requirements.txt for that environment. Joblib artifacts must be trained and served using the same scikit-learn version; retrain after a dependency upgrade.

## 2. Run the end-to-end pipeline in a terminal

From the project root, activate the environment and run the complete generated-data demo:

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 python -m src.pipeline --demo
```

This trains/evaluates the models and writes the run outputs to `artifacts/` (the default output directory). To choose another output directory, pass `--output path/to/folder`. The run includes source/augmented EDA, class balance, features, policy validation, held-out evaluation and predictions, queue counts, explanations, sensitivity/calibration reports, a serving bundle, an example request and a generated technical note. Existing files with matching names in the output directory are overwritten.

Run the automated tests after the pipeline completes:

```bash
python -m pytest -q
```

To reproduce results from CMS data instead, place the required Sample 1 files under `data/raw/` as described below and run:

```bash
OMP_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 python -m src.pipeline --raw data/raw --output artifacts
```

The command-line pipeline defaults are `--raw data/raw`, `--config config.json`, and `--output artifacts`. `--demo` switches to generated data and does not require CMS files. CMS and demo runs both produce a bundle at `artifacts/bundle.joblib`; rerun the pipeline after changing the data mode if you want the API to serve that run.

## 3. Run the API endpoints

First complete a pipeline run so `artifacts/bundle.joblib` exists. Start the API from the project root:

```bash
python -m uvicorn src.api:app --host 127.0.0.1 --port 8000
```

Leave that process running and use a **second terminal** for requests. The interactive API documentation is at http://127.0.0.1:8000/docs. Or call the endpoints with curl:

```bash
# Health and loaded model/data mode
curl http://127.0.0.1:8000/health

# Score the example claim generated by the pipeline
curl -X POST http://127.0.0.1:8000/score \
  -H 'Content-Type: application/json' \
  --data-binary @artifacts/example_claim.json

# Score a batch (the endpoint expects an object containing a "claims" array)
curl -X POST http://127.0.0.1:8000/score-batch \
  -H 'Content-Type: application/json' \
  --data '{"claims":[{"claim_id":"example-1","member_id":"member-1","submitted_at":"2010-01-01T00:00:00","service_from":"2009-12-31","service_to":"2009-12-31","birth_date":"1942-08-01","diagnosis_codes":["72142"],"lines":[{"provider_id":"provider-1","hcpcs_code":"97032","diagnosis_code":"7231","submitted_amount":134.32}]}]}'
```

Both scoring endpoints return class probabilities, risk score and recommended queue. `/score-batch` applies review capacity only within that request; it is not a persistent daily queue manager.

## 4. Run with CMS data

Official downloads and schema:
- https://www.cms.gov/data-research/statistics-trends-and-reports/medicare-claims-synthetic-public-use-files/cms-2008-2010-data-entrepreneurs-synthetic-public-use-file-de-synpuf/de10-sample-1
- https://www.cms.gov/research-statistics-data-and-systems/downloadable-public-use-files/synpufs/downloads/synpuf_dug.pdf

Place the following **Sample 1** archives OR extracted CSVs in `data/raw/`. Keep one format only so records are not read twice. Preserve original filenames.

1. Carrier Claims Sample 1A, 2008–2010.
2. Carrier Claims Sample 1B, 2008–2010.
3. Beneficiary Summary Sample 1 for 2008, 2009, 2010.

Do not use the Sample 20 file mistakenly linked in the provided 2010 URL. Only baseline 2008 date of birth is used as a model input; annual condition, reimbursement and death fields are excluded. The other beneficiary years can be used for exploratory checks, but are not needed for the present predictive feature set. Inpatient/outpatient/PDE are intentionally out of scope.

The pipeline samples 5,000 members using a fixed seed and retains all their carrier histories. Increase `sample_members` in config.json if a temporal partition lacks the rare class. It reads the full carrier archives in chunks twice: first to select members, then to load their claims. This may take several minutes. It fails clearly on incorrect schemas, conflicting claim IDs or insufficient class coverage.

After the run finishes, the reports and `bundle.joblib` are in `artifacts/`. Run tests using the command in the terminal workflow section. Start the API separately using the API instructions above.

## 6. Target construction

Target is **outcome risk**, not queue. Class order: 0 clean, 1 denial risk, 2 FWA risk. These are mutually exclusive simulation outcomes; real denial and FWA could overlap.

| Scenario probability | Scenario | P(clean), P(denial), P(FWA) |
|---:|---|---|
| 0.86 | Ordinary claim | 0.985, 0.012, 0.003 |
| 0.04 | Amount inflation | 0.40, 0.30, 0.30 |
| 0.04 | Repeat submission | 0.30, 0.65, 0.05 |
| 0.03 | Unusual pairing | 0.75, 0.23, 0.02 |
| 0.03 | Provider submission cluster | 0.65, 0.15, 0.20 |

Expected overall mixture is about 91.7% clean, 5.9% denial and 2.4% FWA before finite-sample variation and edge cases. Actual balance is exported by partition. Every scenario can produce clean claims; ordinary claims can produce adverse labels. No deterministic flag or simulation scenario enters X. Provider IDs are lookup keys only. The rule reference helps identify circular label recovery. This simulation does not validate clinical code compatibility.

DE-SynPUF carrier files do not include submitted billed amount or place of service. Submitted amount is simulated from positive allowed-charge scales with multiplicative noise; missing/nonpositive scales fall back to training-period procedure medians. This is an augmentation, not an assertion that allowed amount is billed amount. All original allowed/payment/processing variables are discarded before modeling. No unsupported coverage termination or unbundling claim is made.

## 7. Temporal design

- Warm-up: submissions before 2008-04-01; used for frozen procedure medians and code co-occurrence, excluded from fitting.
- Training: 2008-04-01 through 2008-12-31.
- Calibration: 2009-01-01 through 2009-06-30.
- Model/policy selection: 2009-07-01 through 2009-12-31.
- Test: 2010 onward within the source data.

Submission timestamp is explicitly simulated as service end plus one day. All member/provider/duplicate features exclude the submission day; no full-day totals leak into earlier scores. History may grow across evaluation periods using already observed submissions, never their outcomes. Duplicates and their original claim stay in the same calendar partition. IDs are never encoded as direct features. Static birth date comes from the baseline file; yearly chronic-condition/reimbursement/death flags do not enter X.

## 8. Routing assumptions and boundaries

Costs in dollars: standard review $10, senior review $30, auto-paid adverse denial $200, auto-paid FWA $2,000. Review detection probabilities for denial/FWA: 90%/50%; senior: 95%/90%. These are assumptions, not measured reviewer performance.

For probabilities d=P(denial), f=P(FWA):

- Auto expected cost: `200*d + 2000*f`.
- Review expected cost: `10 + 20*d + 1000*f + penalty`.
- Senior expected cost: `30 + 10*d + 200*f + penalty`.

Thus review beats auto when `180*d + 1000*f > 10 + penalty`; senior beats auto when `190*d + 1800*f > 30 + penalty`; senior beats review when `10*d + 800*f > 20`. The chosen penalty is selected on policy validation, not test. These are transparent action boundaries, not arbitrary .5/.8 probability cutoffs.

Daily batch allocator ranks positive expected-loss reductions under 100 standard and 20 senior slots. It is greedy, not globally optimal. **Single-claim recommendations do not enforce capacity.** Batch capacity applies only within the supplied batch: concurrent requests need a persistent transactional queue manager. The serving feature store is an immutable snapshot and does not update with new requests; production must ingest new history separately and atomically. Reasons are generated for all reviewed/high-risk test claims, and on demand for API decisions.

## 9. Outputs

- `source_eda.json`, `source_*_counts.csv`: original source missingness, amount quality, code frequencies and monthly volume before labeling.
- `eda_summary.json`, `eda.png`: cleaning, augmented descriptive statistics and plots.
- `class_balance.csv`, `simulation_audit.json`: outcomes and labeling audit, separate from X.
- `features.csv`: model inputs only.
- `policy_validation.json`: pre-test model-selection metrics.
- `evaluation.csv`, `evaluation.png`: held-out model comparison, PR and calibration.
- `test_predictions.csv`, `daily_queue_counts.csv`: probabilities and capacity-constrained queues.
- `review_explanations.json`: reasons for every reviewed/high-risk test claim.
- `calibration_bins.csv`, `sensitivity.csv`: reliability and cost/capacity scenarios.
- `bundle.joblib`, `example_claim.json`, `run_manifest.json`: serving bundle and input fixture.
- `technical_note.md`: concise note populated with the actual run results.

The model with lowest policy-validation expected cost is selected; it may be logistic rather than boosting. All candidates are evaluated on test, but test results do not change model selection. Reviewing everything is a deliberately unconstrained policy reference. Expected test cost uses synthetic labels and assumed interception rates, rather than the model's own predicted probabilities alone.

## 10. Limitations / production work

Synthetic labels, simulated amounts/timestamps, simplified code groups and frozen reference distributions limit validity. No actual denied/fraud outcomes, coverage checks, modifiers or clinically validated unbundling policies are supplied. Explanations use one-at-a-time replacement; interactions and correlated features can make them misleading. Calibration temperature is scalar and does not fully correct weighted class bias. Source is old, synthetic, and not representative of current payer traffic. A production release needs authentication, privacy controls, an append-only historical store, audited reviewer outcomes, a real capacity manager, code-set versioning, subgroup validation and prospective monitoring. Keep model artifacts private if replacing this demo with real data.
